## 9. System Health Metric

**What to Optimize For:** **Verified Completeness Rate** - The percentage of complex, multi-component tasks where the model produces outputs that pass expert verification on all dimensions simultaneously.

**Why This Metric:**
The creator's testing methodology reveals the critical insight: models can excel on isolated benchmarks while failing on real work that requires multiple capabilities simultaneously. O3's advantage isn't raw intelligence on single dimensions - it's **completeness across dimensions**:
- Civilization simulator: narrative richness + logical consistency + self-critique quality
- Multimodal mystery: story coherence + image generation + text embedding + answer key accuracy
- Peer review: research quality + perspective-shifting + rebuttal strength

A model can pass each component individually but fail the integrated task. The metric must capture: "Did it actually complete what work requires?"

**How to Measure:**
1. **Define Task Taxonomy:** Map work tasks to multi-skill requirements (e.g., "strategic memo" requires research + synthesis + persuasion + counter-argument + formatting)
2. **Expert Verification Protocol:** Subject matter experts verify all components, not just overall impression
3. **Component Tracking:** Log which specific elements failed (e.g., "image contained no readable text despite claim")
4. **Longitudinal Comparison:** Track Verified Completeness Rate across model versions and competing models
5. **Failure Analysis:** When Verified Completeness fails, categorize why (missing component, hallucinated element, logical inconsistency, etc.)

**Practical Implementation:**
- Sample 20-30 representative work tasks per week
- Run through O3 and alternatives side-by-side (same prompt)
- Expert review scores each dimension 0-1
- Verified Completeness = 1 only if ALL dimensions score 1
- Track weekly rolling average
- Alert if rate drops below threshold (suggests capability regression or misalignment)

- **Alignment Risk Emerges From Strengths, Not Weaknesses:** The danger isn't that O3 is bad - it's that it's so persuasive, logical, and confident that humans won't notice when it's wrong. "The model's weaknesses come from those strengths."

## 11. Application & Mental Model

### When to Use This Pattern

**Custom Benchmarking Over Published Metrics:**
- When evaluating tools for real work (not research)
- When published benchmarks feel suspiciously high
- When you need to understand actual work-task performance
- When comparing "everyday tool" alternatives

**Signals This Approach Is Relevant:**
- Model claims don't match your experience
- Marketing emphasizes benchmark scores
- You need multi-skill task completion
- Competitive landscape shifting rapidly
- Usage patterns will generate proprietary data

**Critical Recognition:** "That's the feeling I had yesterday...my preconceptions about what LLMs were capable of were going to change again." When your gut tells you something fundamental shifted, invest time in rigorous testing.

### When NOT to Use This Pattern

**Avoid Custom Benchmarking When:**
- Evaluating highly specialized technical capabilities (use domain benchmarks)
- Time-to-decision is critical (published benchmarks are faster)
- You lack domain expertise to verify completeness
- Task is simple/single-dimensional (overhead not worth it)
- Model choice isn't strategic (low switching cost, no data flywheel)

**Wrong Contexts:**
- Pure research evaluation (published benchmarks appropriate)
- One-off usage (learning curve not worth investment)
- Tasks where "good enough" suffices
- When verification costs exceed value of accuracy

**When O3 Isn't the Right Choice:**
- Creative/emotional writing (4o currently better due to output constraints)
- When mathematical bias is problematic
- Cost-sensitive high-volume applications
- Until availability constraints resolve
- When older models' weaknesses are well-mapped and manageable
