2. Model Selection: Opus vs. Sonnet on Teams

2.1 What’s Available on Teams Plan

On Claude Teams, users can manually switch models via a dropdown
selector at the top of the chat interface. Available models include Opus
4.6, Opus 4.5, Sonnet 4.5, and Haiku 4.5. Your selection persists across
conversations until you change it.

2.2 Is Thinking Adaptive?

  -------------------------- --------------------------------------------
  Model                      Thinking Behavior

  Opus 4.6                   ADAPTIVE by default. Automatically allocates
                             thinking effort based on task complexity.
                             Simple email = quick. Complex itinerary =
                             deep thinking. No prompt instructions
                             needed. Also has adjustable effort levels
                             (low/medium/high) in Claude Code.

  Opus 4.5                   Has extended thinking capability but it’s
                             NOT adaptive by default in the same way as
                             4.6. On Teams via claude.ai, extended
                             thinking is available and can be toggled.
                             For complex tasks, you may benefit from
                             explicitly prompting “analyze before
                             drafting.” The v3 golden prompt already
                             includes this instruction, so you’re
                             covered.

  Sonnet 4.5                 Extended thinking available but NOT
                             adaptive. Needs explicit activation.
                             However, for DMC email/proposal work, Sonnet
                             4.5 is capable enough without extended
                             thinking. It handles 90% of tasks at high
                             quality. Reserve extended thinking for
                             complex pricing analysis or multi-day
                             itinerary design.

  Haiku 4.5                  No extended thinking. Fast and cheap. Not
                             recommended for client-facing work. Could be
                             used for quick internal questions or simple
                             lookups.
  -------------------------- --------------------------------------------

Your idea of varying the model per task is excellent and totally doable.

consider upgrading to Max.

In the previous document, I recommended the Router because I was worried

Claude doesn’t load everything — it retrieves selectively. This makes
the 1-project approach much more viable than I initially thought.

3.2 Should the Router Do RAG/M365 Search?

No. The Router should be fast and light. Here’s why:

- The Router’s job is: understand the task, prepare a prompt, direct to
  the right project. It doesn’t need client history for that.

- If the Router does M365 search, it spends time and tokens pulling
  client data that will be pulled AGAIN when the lean project runs the
  golden prompt.

- Double-RAG wastes tokens and slows down the workflow.

Exception: If the Router needs to check something to determine which
project to use (e.g., “is this an existing client or cold outreach?”), a
quick M365 search is fine. But the deep context pull happens in the lean
project.

+-----------------------------------------------------------------------+
| ROUTER OUTPUT FORMAT                                                  |
|                                                                       |
| Router responds with:                                                 |
|                                                                       |
| 1. Task type identified: “This is a follow-up email to a returning    |
| client”                                                               |
|                                                                       |
| 2. Project to use: “Client Communications”                            |
|                                                                       |
| 3. Pre-filled prompt ready to paste (with client name, email chain,   |
| and context pre-injected)                                             |
|                                                                       |
| 4. Model recommendation: “Sonnet is fine for this” or “Switch to Opus |
| — this is a complex proposal”                                         |
|                                                                       |
| Staff copies the pre-filled prompt, opens the right project, pastes,  |
| done.                                                                 |

3.3 Best Lines Doc: One Master or Per-Project?

One master Best Lines doc, uploaded to each project that needs it.

A single master document keeps maintenance simple. When Friday review
adds a new great line, Patrick updates one file and uploads it to the
2–3 projects that use it. If you had separate docs per project, you’d be
maintaining 4–5 copies and they’d drift apart.

Yes, this is separate from the golden prompts. The golden prompt is the
instruction template. The Best Lines doc is a reference library of
proven language. Claude reads both and weaves the best lines into
prompt-driven outputs. They complement each other.

Does it hurt performance to RAG the Best Lines doc?

No. Project Knowledge files are either loaded directly (if small) or
retrieved via RAG (if large). A Best Lines doc of 2–5 pages is small
enough to be loaded directly and doesn’t meaningfully impact context
budget. RAG overhead only matters for large document collections.

4. Can One Email Prompt Handle All 10 Types?

Yes. The v3 dynamic prompt is designed for exactly this. Here’s why it
works and when it might not:

The v3 prompt tells Claude to ANALYZE the email chain first, classify
the type, then adapt its approach. With 10 different example emails in
Project Knowledge (one per type), RAG pulls the most relevant example.
The DO’s and DON’Ts catch type-specific rules. Claude maps the incoming
email to the closest type and writes accordingly.

When this might break down:

- Highly specialized email types with unique formatting (e.g., a legal
  notice template or a specific booking confirmation format). These need
  rigid structure, not dynamic judgment.

- If a particular email type consistently rates 2/4 or 1/4, that’s the
  signal to either add a more targeted example or create a specialized
  sub-prompt.

Practical approach: Start with 1 prompt + 10 examples. Monitor ratings
by email type in Friday review. If a specific type consistently
underperforms, create a specialized prompt for that type only. Don’t
split prematurely.

6. Data Indexing & How RAG Works in Practice

6.1 Two Different RAGs (Don’t Confuse Them)

  -------------------------- --------------------------------------------
  System                     How It Works

  Project Knowledge RAG      When your uploaded files exceed the context
                             window, Claude’s built-in RAG searches your
                             Project Knowledge files and retrieves only
                             relevant sections. This happens
                             automatically. You don’t control it. It’s
                             efficient and well-optimized.

  M365 Connector Search      When you ask Claude to “search our M365
                             for...”, it runs a search query against
                             Microsoft’s search index. Returns relevant
                             email snippets, document excerpts, Teams
                             messages. This is NOT RAG in the traditional
                             sense — it’s a search API call. Results are
                             injected into the conversation context.
  -------------------------- --------------------------------------------

Context budget per conversation:

200K tokens total. Breakdown: Project Knowledge files loaded directly or
via RAG (~20–50K typical) + M365 search results (~5–20K per search) +
your prompt + Claude’s response + conversation history. For a typical
email task, you’re using maybe 30–70K tokens. Plenty of headroom.

7. Optimizing Project Context

You asked: Claude doesn’t need to see all prompt templates since it
knows what kind of email it needs. How do we prevent it from reading
everything?

Answer: RAG already handles this. On your Team plan, when Project
Knowledge is large enough, Claude doesn’t load everything. It reads the
system prompt and small files directly, then uses RAG to retrieve only
the relevant larger files based on the current conversation.

What you CAN control:

- System prompt (Custom Instructions): Always loaded in full. Keep this
  under 2,000 words. This is your golden prompt template and core
  instructions.

- Small files (<2K tokens each): Likely loaded directly. Put your
  DO’s/DON’Ts, Best Lines, and tone guide here. These are always
  relevant.

- Large files / many examples: RAG retrieves selectively. Your 10
  example emails here. Claude pulls the one that matches the current
  task.

Practical tip: Name your example files clearly.
“Example_Email_Cold_Outreach.txt”,
“Example_Email_Complaint_Response.txt”, etc. Good file names help RAG
match the right example to the right task.
