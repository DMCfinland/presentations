1. The Feedback Architecture (Corrected)

1.1 How Staff Logs Feedback (Zero Extra Tokens)

You’re right that Claude shouldn’t waste Opus tokens acknowledging
feedback. The solution: add an instruction to the Project System Prompt
(the custom instructions field in Project settings) that tells Claude
how to handle feedback.

+-----------------------------------------------------------------------+
| ADD THIS TO YOUR PROJECT SYSTEM PROMPT (Custom Instructions)          |
|                                                                       |
| FEEDBACK HANDLING:                                                    |
|                                                                       |
| When the user’s message starts with “FEEDBACK:” or contains a rating  |
| like “3/4” or “4/4” at the end of a conversation after a task is      |
| complete:                                                             |
|                                                                       |
| • Respond ONLY with: “✅ Logged.”                                     |
|                                                                       |
| • Do NOT elaborate, do NOT ask follow-up questions, do NOT summarize  |
| the feedback.                                                         |
|                                                                       |
| • Do NOT use extended thinking for this response.                     |
|                                                                       |
| • This saves tokens. The feedback value is in the human’s text, not   |
| Claude’s response.                                                    |
+-----------------------------------------------------------------------+

What this looks like in practice:

+-----------------------------------------------------------------------+
| STAFF MEMBER’S FINAL MESSAGE IN CONVERSATION                          |
|                                                                       |
| FEEDBACK: 3/4. Had to shorten the reply — client asked a quick date   |
| question but Claude wrote a full itinerary pitch. For short           |
| questions, match the length. Otherwise tone and personalization were  |
| excellent.                                                            |
+-----------------------------------------------------------------------+

+-----------------------------------------------------------------------+
| CLAUDE’S RESPONSE (2 tokens, not 200)                                 |
|                                                                       |
| ✅ Logged.                                                            |
+-----------------------------------------------------------------------+

The feedback now lives in the conversation. But since other
conversations can’t see it, we need to extract it somewhere central.

1.2 Where Feedback Actually Goes: The Shared Sheet

Since Claude Projects don’t share conversation history, feedback must be
extracted to a shared location Claude can read. The simplest solution: a
shared Excel file on SharePoint.

But wait — doesn’t that add friction?

Minimal. Here’s the optimized flow: after Claude responds “✅ Logged”,
the staff member copies their feedback text (which they just typed) and
pastes it as a new row in the shared Excel. This takes 15 seconds.
They’re already in the habit of switching to Outlook to paste the email
reply, so one more paste into Excel is marginal.

Alternative for absolute minimum friction:

Staff sends their feedback to a shared Teams channel called
“#ai-feedback.” Just paste the same feedback text as a Teams message.
Claude can search Teams via the M365 connector on Friday. This might be
even simpler than Excel since everyone already has Teams open.

  ------------------------- ---------------------------------------------
  Method                    Trade-off

  Teams channel             Lowest friction (paste into Teams). Claude
  #ai-feedback              searches it via M365 connector. Less
                            structured data. Best for Weeks 1–4.

  Excel on SharePoint       Slightly more friction (open Excel, paste
                            row). More structured. Better for
                            dashboard/trending. Best for Month 2+.

  Both                      Start with Teams channel. Migrate to Excel
                            when you need charts/trends. The Teams
                            messages become the source for populating
                            Excel.
  ------------------------- ---------------------------------------------

3. The Big Architecture Decision: Router vs. Separate Projects

3.1 The Problem

You identified this perfectly: if we have 10 different email types, each
with 3–5 examples, that’s 30–50 example files. If they all sit in one
project, Claude loads ALL of them into every conversation. That’s wasted
context on 9 email types when you only need 1.

But 10 separate projects means staff have to decide “which project do I
open?” before every task. That’s friction and decision fatigue.

  Projects           Staff picks the right one.     files loaded. But

  Projects           task. 3–4 lean projects for    tiny. Execution

3.3 The Router Architecture in Detail

Project 1: “DMC Router” (the starting point for everything)

Project Knowledge contains:

  which project to use

- The router system prompt (in Custom Instructions)

|                                                                       |

- Staff always starts in the same place (DMC Router). No decision

- Router analyzes the task and either handles it directly or sends staff

- Specialized projects stay lean — only the relevant examples and
  context loaded.

- Router uses minimal context (small prompt map + basic company info).
  Cheap and fast.

4. DO’s, DON’Ts, and Best Lines

You asked two questions: should we include DO’s and DON’Ts, and does
Claude pick up best practices from the example emails alone?

Answer: Both. They serve different purposes.

  ------------------------- ---------------------------------------------
  Source                    What Claude Learns From It

  Example emails (3–5)      Implicit patterns: tone, structure, length,
                            what “great” looks like. Claude mimics these
                            naturally. Works well for style and flow.

  DO’s and DON’Ts doc       Explicit rules: things Claude must
                            always/never do that might not be obvious
                            from examples alone. Safety rails. Hard-won
                            lessons from mistakes.

  Best Lines & Phrases doc  Specific language that works well with your
                            clients. Signature phrases, proven openers,
                            effective CTAs. Claude weaves these in
                            naturally.
  ------------------------- ---------------------------------------------

Examples teach Claude what good looks like. The DO’s/DON’Ts prevent
specific failure modes. Best Lines give Claude proven building blocks.
You need all three.

5. Thinking Effort, Skills, and Model Behavior

5.1 Does Claude Need “Think Harder” Instructions?

No. Claude Opus 4.6 adapts its reasoning effort automatically based on
task complexity. A simple date-check email gets quick processing. A
complex multi-day itinerary with pricing gets deep thinking. You don’t
need to include instructions like “think step by step” or “use extended
thinking.” The model handles this natively.

Exception: If you’re on Sonnet 4.5 (which Teams might use for some
conversations to manage costs), explicit “analyze before drafting”
instructions help more. The v3 golden prompt already includes this with
the “ANALYZE FIRST, THEN DRAFT” section, which works well on both
models.

5.2 Could Claude Skills BE the Golden Prompts?

Interesting idea. Claude Skills (in claude.ai) are custom instructions
you can apply to any conversation. They’re similar to Project system
prompts but can be toggled on/off and shared. In theory, you could
create a Skill called “DMC Email Drafter” that contains the golden
prompt.

However, Skills have limitations vs. Projects:

- Skills are text-only instructions. They can’t include uploaded files
  (example emails, tone guide, service catalog).

- Projects can hold multiple knowledge files that Claude reads as
  context. Skills cannot.

- Skills work best for short, reusable instructions. Golden prompts that
  need rich context work better in Projects.

+-----------------------------------------------------------------------+
| VERDICT ON SKILLS                                                     |
|                                                                       |
| Use Skills for simple, portable instructions (e.g., “Always write in  |
| Finland DMC’s tone” that applies everywhere).                         |
|                                                                       |
| Use Projects for context-rich workflows (e.g., email drafting with    |
| examples, tone guide, client search).                                 |
|                                                                       |
| They’re complementary, not interchangeable. Your golden prompts live  |
| in Projects. A general “DMC brand voice” Skill can sit on top.        |
+-----------------------------------------------------------------------+

6. Phone Call Logging: Where Copilot Actually Matters

Your friend is right. This is Copilot’s genuine killer feature and the
most likely reason you’ll eventually add it. Teams calls with Copilot
automatically get: transcription, summary, action items, and searchable
notes. Without Copilot, phone call content is lost — it never enters the
system.

Why this matters for your AI system:

Right now, if a staff member has a 20-minute phone call with a client
about their Lapland trip preferences, that intelligence disappears.
Claude can’t find it. Next time someone emails the client, Claude’s M365
search misses the phone conversation entirely. The email reply is less
personalized because key context was never captured.

With Copilot on Teams calls:

- Client says on the phone: “We’d love to do dog sledding but two people
  in our group are afraid of dogs”

- Copilot captures this in the meeting transcript/notes

- Next time Claude searches M365 for this client, it finds the note

- Claude’s email draft says: “For outdoor activities, we’ve selected
  reindeer safari and snowmobile excursion, which the whole group can
  enjoy”

- Client is impressed we remembered. Conversion rate goes up.

+-----------------------------------------------------------------------+
| COPILOT DECISION POINT                                                |
|                                                                       |
| Don’t add Copilot in Week 1. It’s not needed for the core workflow.   |
|                                                                       |
| ADD Copilot when: you’ve confirmed that phone calls are a significant |
| data gap. If your team has 5+ client calls per week and keeps losing  |
| intelligence, Copilot pays for itself through better email            |
| personalization alone.                                                |
|                                                                       |
| Budget for this: Month 2–3 evaluation. €90–105/mo for 5 users.        |

7. Context Management: Keeping RAG Under Control

You raised the right concern: too much context can actually hurt
performance. Here’s how to manage it.

7.1 How Project Knowledge Affects Performance

The rule: Every file in Project Knowledge is loaded into Claude’s
context window for every conversation in that project. More files = more
context used = less room for the actual conversation = potentially
diluted attention.

  ------------------------- ---------------------------------------------
  Project Knowledge Size    Effect on Performance

  5–10 focused files (~20   Optimal. Claude reads all, applies relevant
  pages)                    parts. No dilution.

  15–25 files (~50+ pages)  Starting to crowd. Claude may miss details.
                            Less room for conversation.

  50+ files                 Too much. Claude’s attention dilutes.
                            Performance degrades. Context window fills
                            up.
  ------------------------- ---------------------------------------------

For your Email Drafts project, target 6–8 files max:

1.  Tone of voice guide (1–2 pages)

2.  DO’s and DON’Ts (1 page, grows slowly)

3.  Best Lines & Phrases (1 page, grows slowly)

4.  3–5 example emails (1 page each)

5.  Golden prompt template (1 page)

That’s roughly 8–12 pages of context. Well within the optimal range.
Claude reads it all, attention stays sharp, and there’s plenty of room
for the email chain and M365 search results.

7.2 The 200-Chat Question

200 conversations in one project does NOT affect context or performance.

Each conversation is completely independent. Conversation 201 does not
see conversations 1–200. The only thing that persists across
conversations is the Project Knowledge files. So having lots of
conversations is fine — they don’t accumulate or create “context rot.”

What CAN rot context within a single conversation:

- Very long conversations (50+ back-and-forth messages). Claude’s
  attention on early messages weakens.

- Mitigation: For new tasks, start a new conversation. Don’t reuse a
  30-message chat for a new email.

7.3 M365 Connector Search: What Gets Loaded?

When Claude searches your M365 data, it doesn’t load your entire mailbox
into context. It runs a search query and receives relevant
snippets/summaries from matching results. This is managed by Microsoft’s
search infrastructure, not by Claude’s context window.

What this means practically:

- Your shared mailbox having 10,000 emails is fine. Claude searches,
  gets the relevant 5–10 snippets, and uses those.

- The M365 search quality depends on Microsoft’s indexing.
  Well-structured emails with clear subjects are found better.

- Large attachments (50-page PDFs) are not fully loaded. Claude gets
  metadata and key excerpts. If you need the full document, upload it
  directly to the conversation.

+-----------------------------------------------------------------------+
| SHARED MAILBOX ADVANTAGE                                              |
|                                                                       |
| Having a shared mailbox is excellent for this system. All client      |
| correspondence is in one searchable location. When Claude searches    |
| for “past emails with Nordic Adventures,” it finds everything         |
| regardless of which staff member sent/received it. This is better     |
| than individual mailboxes where client history is fragmented across 5 |
| inboxes.                                                              |
